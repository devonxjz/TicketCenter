TicketCenter Architecture Review

Deepening Opportunities for Testability, Navigability & Code Quality

For: newbie-friendly codebase, clean architecture, SOLID principles, design patterns, video tutorials

Architecture Goals

  • 1. Single Config Module: Centralize all application configuration into one coherent AppConfig
  • 2. Consistent MVC per Feature: Each feature-package implements controller → service → repository → model with clean seams
  • 3. Error Tanks: Each feature owns an error/ directory holding all domain-specific exceptions and error codes
  • 4. Code Quality: Follow SOLID principles, use design patterns, reduce complexity, improve navigability
  • 5. Teachability: Structure code so newbies can understand the request flow: servlet → service → repository → stored procedure

Config Consolidation Module

Strong
Problem

Configuration is scattered across multiple files creating initialization chaos and circular dependencies:

  • AppConfig.java, ServerConfig.java, DatabaseConfig.java, MailConfig.java, IdentityConfig.java, PayosConfig.java, TicketQrConfig.java — all at config/ level
  • Plus IdentityContextListener and IdentityServices in identity/config/ — feature-specific config mixed with global
  • Multiple initialization paths: listeners, static blocks, servlet context, @PostConstruct
  • No clear entry point; hard to trace where a config value comes from
  • Tests must boot many subsystems just to read config
Solution

Create a unified AppConfig module as the single entry point for all runtime configuration:

  • AppConfig.java loads environment variables, properties file, and secrets — one constructor
  • Feature-scoped config providers return immutable config objects (no side effects)
  • Move IdentityContextListener and IdentityServices into config initialization (no feature-level listeners)
  • All features depend only on AppConfig, never on each other's config
  • Config is immutable once initialized; no lazy initialization in services
Benefits
  • Locality: All config in one place; developers see the full startup picture immediately
  • Leverage: Tests can inject config without booting the app; mocking becomes trivial
  • Testability: Unit tests create minimal AppConfig; integration tests override specific values
  • Navigability: New developers start at AppConfig and trace feature initialization

Consistent Error Tanks Across Features

Strong
Problem

Error handling is inconsistent and scattered:

  • Some features have an error/ directory: identity/error/IdentityException.java, identity/error/IdentityError.java
  • Others scatter exceptions in service or controller layers: payment/service/PaymentException.java, order/service/OrderException.java, ticketing/service/HoldException.java
  • Error codes and messages are hardcoded in services, not centralized
  • No shared error taxonomy; newbies don't know where to define a new error
  • Testing error paths requires understanding where exceptions live across the codebase
Solution

Create an "error tank" (error/ directory) in each feature, holding all domain exceptions, codes, and validation errors:

  • feature/error/FeatureException.java — domain-specific exception wrapping error code
  • feature/error/FeatureErrorCode.java — enum of all error codes (HTTP status, message template, user-facing message)
  • feature/error/FeatureValidationError.java — struct for field-level validation results
  • Services throw FeatureException with error codes; controllers catch and translate to HTTP responses
  • Integration tests assert on error codes, making tests refactor-safe
Benefits
  • Locality: All errors for a feature in one place; error handling is fully encapsulated
  • Leverage: Controller code: catch(FeatureException e) { return e.toResponse(); }
  • Testability: Tests assert on error codes, not messages; they survive refactoring
  • Navigability: New feature? Create error/ directory with exceptions; done

Deepen MVC Seams with Explicit Dependency Injection

Worth exploring
Problem

The MVC structure exists but is not uniformly deep; dependencies leak across layers:

  • Controllers call services, services call repositories — good so far
  • But services instantiate helpers inline (validators, builders, hashers), blurring the layer
  • IdentityServices is a god object pulling in email, hashing, session cache
  • Dependencies are implicit; tests must set up all services even to test one endpoint
  • Hard to understand what a service needs without reading its constructor
Solution

Strengthen the MVC seams with explicit dependency injection and clear responsibility:

  • Each controller knows only the service interface, not the implementation
  • Each service knows only the repository interface and needed domain services
  • Helper classes (validators, builders) are injected, never instantiated inline
  • Create feature/FeatureComponent.java that wires all feature dependencies
  • Use immutable DTOs at layer boundaries; no entity mutation across layers
Benefits
  • Locality: Reading a servlet, you see exactly its dependencies; wiring is explicit
  • Leverage: Mock the service interface; test the servlet without touching the database
  • Testability: Each layer tested independently with minimal fixtures
  • Navigability: New developer traces servlet → service → repository → SQL; no surprises
Files to Create/Refactor
  • src/main/java/vn/ticketscenter/identity/IdentityComponent.java (create)
  • src/main/java/vn/ticketscenter/order/OrderComponent.java (create)
  • src/main/java/vn/ticketscenter/event/EventComponent.java (create)
  • src/main/java/vn/ticketscenter/*/service/*Service.java (refactor: constructor injection)
  • src/main/java/vn/ticketscenter/*/controller/*Servlet.java (refactor: depend on interface)

Apply Design Patterns & SOLID for Quality

Worth exploring
Problem

Code quality issues reduce navigability and increase maintenance burden:

  • Large services (100+ lines) doing multiple things: validation, logic, persistence
  • Duplicate validation logic across endpoints
  • No clear strategy pattern for different payment/refund flows
  • Magic strings (field names, error codes) instead of constants
  • Mutable DTOs; unclear what fields are read-only vs. writable
Solution

Apply SOLID principles and design patterns systematically:

  • Single Responsibility: Split large services; e.g., OrderValidationService, OrderPlacementService, OrderQueryService
  • Strategy Pattern: Payment strategies (payOS, manual refund) implement a common interface
  • Builder Pattern: DTOs built step-by-step; immutable once created
  • Adapter Pattern: External APIs (payOS, email) behind feature-specific adapters
  • Constants: Move magic strings to feature FeatureConstants.java
Benefits
  • Locality: Each class has one reason to change; understanding is scoped
  • Leverage: New flow? Add a strategy; no existing code changes
  • Testability: Small classes are easier to test; mocking strategies is straightforward
  • Teachability: Newbies see clear patterns; they apply the same to new features
Example: Order Payment Strategies
order/payment/PaymentStrategy.java — interface
order/payment/PayosPaymentStrategy.java — payOS impl
order/payment/ManualPaymentStrategy.java — manual impl
order/service/OrderPaymentService.java — uses strategy

Onboarding Guide & Architecture Documentation

Worth exploring
Problem

New developers have no clear entry point to understand the codebase:

  • SPEC.md is functional spec, not architecture guide
  • No "walkthrough of a request" showing the layers in action
  • No decision record for why features are structured this way
  • Hard to know which files to read to understand a domain concept
Solution

Create developer onboarding guide and architecture decision records:

  • docs/architecture/ONBOARDING.md — "Read the code in this order"
  • docs/architecture/REQUEST-FLOW.md — trace one request end-to-end with file paths
  • docs/adr/ADR-001-feature-based-packaging.md — why package-by-feature
  • docs/adr/ADR-002-error-tanks.md — why each feature owns errors
  • Video script narrating: servlet → service → repository → stored procedure
Benefits
  • Navigability: New person opens ONBOARDING.md, follows the path, understands the system in 30 minutes
  • Teachability: Video narrator narrates request flow; viewers see code structure in action
  • Maintainability: ADRs capture why decisions were made, preventing future regressions

Recommended Deepening Path

  1. Start with Error Tanks (Candidate 2) — Quickest win, lowest risk. Move scattered exceptions into feature/error/. Defines pattern for other features. ~2-3 days.
  2. Then Config Consolidation (Candidate 1) — Medium effort, high impact. Refactor config into single AppConfig. Unblocks clean DI. ~3-5 days.
  3. Deepen MVC Seams (Candidate 3) — Introduce explicit DI, layer boundaries. Makes codebase dramatically more testable. ~1 week.
  4. Apply Design Patterns (Candidate 4) — Extract strategies, builders, validators. Refactor incrementally. Ongoing, ~1 month.
  5. Documentation & Video (Candidate 5) — Once architecture stable, document and record walkthrough. ~3-5 days.

Total effort: 2-3 weeks for core cleanup, then ongoing pattern application. Each step makes the next easier because the design becomes more legible.
